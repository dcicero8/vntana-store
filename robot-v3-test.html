1 · Config passed to $loadScene

A map of arbitrary keys → GLB URLs (plus an optional texture map, unused here). The keys reappear in the assemble callback.

This build loads the platform products in DCicero/configurators (Live Public) — each UUID is resolved at runtime to its GLB blob URL (/products/{uuid}/… → modelBlobId → /assets/products/{uuid}/…/{blob}.glb), and those URLs go to $loadScene. Base arm (v3, bare flange) = 1d60e58e; tools = nozzle/gripper/vacarm/vackit. Note: that resolve endpoint returns 200 only when the product is published LIVE_PUBLIC — a deleted or DRAFT product returns 404 with an empty body (bit us twice: a deleted base arm, then a re-upload left in DRAFT).

viewer[$configuratorMode] = true;              // src no longer drives loads

await viewer[$loadScene](
  {
    model: {
      arm:  '<base blob url>',   // persistent base (uuid 1d60e58e), SAME url every load
      tool: '<tool blob url>',   // swappable part, omitted for "bare arm"
    },
  },
  assemble,                       // (models, textures) => boolean
);

Preload — after the first load, $preload each tool GLB (arm is resident, so only the tools fetch) so the first click on any tool is instant (~50–130ms) instead of stalling on an on-demand fetch (~2.6s).

Diff-aware reuse: arm keeps the same URL across every load, so it is not refetched (the base stays resident). Only the changed tool URL fetches.

Platform-pipeline quirks handled in assemble (Convert Only): the ToolMount empty is dropped, so we derive the mount point from the ToolMountMarker mesh's world-bbox center; and a per-node recenter transform is injected on tools, so we zero every tool node's TRS before mounting. (Re-processing the parts through Preserve Meshes and UVs should remove both, letting us drop this handling.)

2 · assemble(models) — mount + canonical single-model template

const assemble = (models) => {
  const arm = models.arm.scene, sc = viewer.scene;

  // viewer AUTO-RELEASES the old tool when its key's url changes; we just DETACH it from the
  // scene (it may still be attached from our mount). We do NOT dispose() it ourselves.
  if (currentTool && currentTool.model !== (models.tool || null)) {
    currentTool.scene.parent?.remove(currentTool.scene);   // detach only
    currentTool = null;
  }
  // mount the NEW tool at the arm's flange (tool authored origin-at-mount, so identity)
  if (models.tool) {
    const t = models.tool.scene;
    t.position.set(0,0,0); t.quaternion.identity(); t.scale.set(1,1,1);
    (arm.getObjectByName('ToolMount') || arm).add(t);
    currentTool = { model: models.tool, scene: t };
  }

  // the built-in single-model template
  arm.traverse(o => sc.trackNode(o));
  sc.model = models.arm;                 // arm is the persistent base Model, never disposed
  sc.content.add(arm);
  sc.queueMeshGeometryUpdate();
  sc.queueUpdate();
  sc.mixer?.setTime(0);
  if (firstLoad) sc.dispatchEvent({ type: 'content-change' }); // lights+bounds+frames — FIRST load only
  return true;
};

Resource management (per Neven): the viewer auto-releases a model when its config key's URL changes — do not call model.dispose() yourself. But it may still be attached to the scene from your mount, so the caller must detach the outgoing tool (parent.remove).

3 · Camera across a swap (corrected — verified against viewer source)

Goal: a tool swap must not move the camera (YKK-style seamless swap). Ground truth in @vntana/viewer@3.0.0, traced through the source:

  • The reset is controls.jump() snapping to the DEFAULT framing. Every load, $loadScene runs $triggerUpdates(), which re-requests the auto camera props and jumps to them (ControlsMixin: once via updateComplete.then(jump), again via the updates-loaded listener registered in the viewer's constructor). It is not content-change — that only invalidates the scene-graph cache.
  • The jump lands AFTER scene-loaded. $loadScene dispatches scene-loaded before it calls $triggerUpdates() (LoadingMixin), so on scene-loaded the controls still hold the user's live orbit — the correct capture point. (The earlier “already-reset on scene-loaded” note was wrong; there is no fit during loading-change.)
  • The default framing sets distance + target (from bounds) but leaves rotation + fov alone — which is why early half-fixes looked like they preserved the view (only rotation survived).
  • A swap also grows the bounding sphere. assemble tracks the new tool and calls queueMeshGeometryUpdate(), so the content bounds are recomputed (arm+tool vs bare arm differ) and content-bounds-update fires with a larger radius — after scene-loaded. Pinning an absolute metre distance would then leave the grown assembly clipped; the fix is to work in the getters' radius-relative r units (rotation/fov stay absolute rad).

What works now (no rAF clamp): on scene-loaded (before both the reframe and the bounds recompute), snapshot the four camera props via the public getters — distance/target in radius-relative r, so they encode the user's framing ratio against the old radius. Then re-assert that snapshot with jumpCamera() at two points: on updates-loaded (to beat the viewer's own default-framing jump, whose constructor-registered listener fires first) and on content-bounds-update (so the view re-lands proportionally once the larger radius is in effect); released when the load resolves. Because setting an r value re-evaluates against the current radius, the same ratio re-lands as a consistent framing of the resized model — no pop, no clipping.

For Neven: radius-relative units make this robust to the growing sphere with no new API, so the one ask that remains is (a) an explicit “assemble without re-framing / preserve camera” option on $loadScene so callers skip the scene-loaded / updates-loaded / content-bounds-update dance entirely. Also: setCameraDistance has a min clamp (~2 units), which can still bite if the user was zoomed very close before a large-tool swap.

Open questions for the viewer team

• Formalize assembly so attaching models/meshes at nodes doesn't reach into three.js internals (scene.trackNode, scene.model, content.add, manual content-change).

• Hierarchy material edits — change the material of a sub-part inside an already-loaded model (this demo only swaps whole part-GLBs).

• Resource management — the viewer auto-releases a model when its key's URL changes, but leaves it attached to the scene (caller must detach). A helper that both releases and detaches, or clearer ownership, would reduce footguns.

• Camera / re-frame (the big one) — every load runs controls.jump() to the default framing (via $triggerUpdates / updates-loaded), wiping the user's orbit. We preserve it with a capture on scene-loaded + re-apply and jumpCamera() on updates-loaded (see §3). Ask: an explicit “preserve camera / assemble without re-frame” option on $loadScene, plus a public absolute-meters camera getter.

• Publish state vs the resolve API — the public product-resolve endpoint 404s (empty body) for DRAFT/deleted products, which reads identically to a bad UUID. A clearer signal (or a documented “must be LIVE_PUBLIC”) would save debugging.
